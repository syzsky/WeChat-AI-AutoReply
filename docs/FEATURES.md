## 分析：这套东西的真实短板

1. **感知层是最脆的一环**。血量靠颜色条、怪物靠 OCR 认名字，换个客户端皮肤、改个字体、加个特效就可能全废。真正的商业挂机走的是读内存/包，但那属于另一个技术栈，也跨过了本项目的合规边界。
2. **坐标校准是硬门槛**。`layout` 那套归一化坐标必须按你的客户端量一遍，量错了表现是"点了没反应"或"永远判定没到达"，很难从日志看出来。所以 `selftest.py` 比挂机脚本本身更重要。
3. **多开吃 CPU**。OCR 是 ONNX 推理，每帧都要跑，一个角色约 10~20% 单核；8 开就是 1~2 核满载。想再往上必须把 OCR 改成"只在可疑区域跑"或换轻量模型。
4. **反检测只做了节律**。延迟抖动、点击偏移、定时休息能降低"机器味"，但改不了"PostMessage 点击没有真实输入队列"这个事实。服务端如果做输入校验，这套会被识别。
5. **没有持久化任务状态**。进程重启后任务链从头开始（补给计时归零），长时间挂机会出现"刚补给完又去补给"的小概率抖动。

## 建议的实施顺序

1. 先在 Windows 上把 `selftest.py` 跑通 → 校准 `layout` → 单角色 `--dry-run` 跑 10 分钟
2. 单角色稳定后开 2 开验证锁/状态/报表
3. 再补 41（多角色 GUI）和 47（背包满处理），这两个是工作室日常最痛的
4. 42（自动建号）和 46（寻路）投入产出比最低，最后做
